# 一、研究背景（前人做到哪一步）

## 1.1 起点：把图问题文本化喂给 LLM

图广泛用于药物发现、交通预测、金融欺诈检测等场景，但图分析门槛高、需要专家。于是研究者尝试用 LLM 解图问题——把图用自然语言（边列表/邻接表等）描述，再让模型推理输出答案。形式化为 $M(G, Q) \to A$

---
## 1.2 两条技术路线及各自的天花板

### 1.2.1 语言类方法（Language-based）

完全靠自然语言复刻图算法执行过程

- **提示工程类**（NLGraph、GPT4Graph、LLM4DyG、Talk like a Graph 等）：探索不同图表示格式（边列表、GML、GraphML）和不同提示策略（zero-shot、few-shot、CoT）
	- 瓶颈：图结构太复杂，LLM 记不住；图一大一密，token 暴涨，长文本下性能下降、推理时间激增。要算对就得复刻算法的迭代+回溯路径，但 **"重复迭代与回溯操作"** 让模型难以输出完整正确的推理链，规模越大越崩
- **微调类**：
	- **GraphWiz**：构造带显式推理路径的数据集，用 SFT + DPO 训练，能输出推理路径。但 **过拟合** 到训练的 9 类任务，换题就套错模板
	- **GraphToken**：用 GNN 把图编码成 GraphToken 对齐文本 token。问题是依赖任务专属编码器，跨任务迁移性能暴跌
	- **GITA**：模仿人类靠可视化理解图，用视觉 LLM（VLLM）看图再推理。但只适合小图，图一大可视化就乱，反而帮倒忙
### 1.2.2 代码增强类方法（Code-augmented）

让模型生成代码，执行得答案 $M(G,Q) \to C,\ \text{exec}(C) \to A$

- **GraphTeam**：多智能体协作，建一个含图 API 文档（如 NetworkX）和执行经验的知识库，检索后辅助编码 agent 写代码
- **GCoder**：用 SFT + 编译器反馈强化学习（RLCF）增强调用图 API 的能力，遇新任务从自建代码库检索相似代码辅助生成
	- 共同瓶颈：**依赖图算法 API 和外部知识库**。一是 API/知识库没覆盖的问题解不了；二是学的是"如何调 API"而非"算法本身"，没真正提升模型的图推理能力（GCoder 还有和 GraphWiz 类似的多任务微调跨任务退化问题）

---
## 1.3 基准测试层面的问题

- 旧基准（NLGraph、Talk like a Graph、GraphWiz、GraphArena、GraphInstruct）几乎都聚焦 **经典图算法任务**，标准 API（NetworkX）就能直接解
- 训练/测试任务重叠，模型可能只是 **记住固定模式** 而非真会推理（Zhang et al. 2024b 证明了这点：合成经典算法数据集训练主要教会模型学固定模式，遇到没见过的任务或换种描述就泛化失败）
- 加上预训练 LLM 本就知道经典图算法，导致旧基准过于简单、缺乏区分度。此外还有无统一评测标准、数据本身有错（如 GraphWiz 的 Hamilton Path、Subgraph Matching，GraphInstruct 的 MST、PageRank）等问题

> [!summary] 一句话收束
> 前人在两条路上都遇到了硬天花板——语言类被"迭代回溯"拖垮、代码类沦为"API 调用器"，而且现有基准太简单、藏着记忆泄漏和数据错误，无法真正衡量图推理能力。这就为本文"重新思考推理焦点 + 造更难的基准"留出了空间

# 二、拟解决的问题（为什么现有方法不行）

本文把"现有方法不行"拆成 **方法** 和 **基准** 两个层面，根子上是一个被忽视的判断：**问题不在基座模型能力不足，而在推理焦点用错了地方**
## 2.1 方法层面：两条路线各有死穴
### 2.1.1 语言类方法 —— 被"重复迭代与回溯操作"拖垮

- 要算对答案，模型必须用自然语言 **完整复刻图算法的执行轨迹**（一步步访问节点、入队出队、回溯）
- 但图算法天然充满迭代和回溯，token 消耗随图规模膨胀；长文本又会进一步拖累 LLM 推理。
- 结果：难以输出完整且正确的推理链，**准确率低、扩展性差**，图越大越崩
- 微调类（GraphWiz/GCoder）还叠加 **多任务微调过拟合**：在训练任务上表现好，换任务就套错模板、性能暴跌
### 2.1.2 代码增强类方法 —— 绕开了真正的图推理
- 让模型调 API、写代码，确实规避了"迭代回溯"问题，但代价是 **依赖图算法 API + 外部知识库**
- 死穴有二：
	- API/知识库 **覆盖不到** 的问题（需要变形或新设计算法）直接失效
	- 学的是 **"怎么调用 API"而非"算法本身"**，没有真正增强模型的图推理能力
- 一句话：它把图推理 **外包** 给了现成工具，回避而非解决了核心问题

---
## 2.2 基准层面：现有基准评不出真实能力

- **任务太简单**：旧基准几乎全是经典图算法任务，NetworkX 等标准 API 就能直接解，预训练 LLM 本就知道这些算法

- **记忆泄漏**：训练/测试任务重叠，模型可能只是 **记住固定模式**，而非发展出真正的图推理能力；遇到没见过的任务或换种描述就泛化失败（Zhang et al. 2024b）

- **缺乏统一评测**：各家用自己的数据集、输出格式不统一（如最短路要不要输出路径），导致比较不公平

- **数据本身有错**：GraphWiz 的 Hamilton Path（判定逻辑 bug，把有解判成无解）、Subgraph Matching（误用 monomorphic 而非 isomorphic 函数），GraphInstruct 的 MST（缺边权）、PageRank 等都存在错误，且被后续工作沿用，污染了整个领域

> [!important] 核心症结
> 现有研究默认"基座模型图推理能力差"，于是要么硬逼模型用语言复刻算法（撞上迭代回溯墙），要么干脆用 API 把推理外包掉（绕过了能力本身）。两者都没回答一个问题：**如果把基座模型的推理焦点从"复刻算法"改成"设计算法"，它到底行不行？** 而旧基准因为太简单、有泄漏、有错误，根本无法回答这个问题——这正是本文要同时打掉的两块绊脚石

---
# 三、创新点与贡献

本文的核心洞察是一次 **推理焦点的转向**：不再逼 LLM 用语言复刻图算法的执行轨迹，而是让它 **设计算法**，再交给代码精确执行。围绕这一洞察，贡献分三层
## 3.1 重新审视 LLM 图推理，指出阻碍进步的真问题

- 把现有方法系统归因为两类死穴：语言类被 **"重复迭代与回溯操作"** 拖垮；代码增强类 **忽视了图问题求解中的关键推理**，沦为 API 调用器
- 提出被长期忽视的判断：**基座模型（如 GPT-4o-mini）被严重低估**，问题不在能力而在用法——焦点从"复刻算法"redirect 到"设计算法"后，基座模型就能解掉旧基准里的大部分任务

---
## 3.2 构建更难的 GraphAlgorithm 基准

- 从 **Codeforces、AtCoder、CodeChef、Kattis** 四个竞赛平台人工筛选题目，过滤处理后得到 **239 个不同问题、3,041 个测试实例**
- 两大特性彻底区别于旧基准：
	- 题目需要 **变形已有算法或设计全新算法**，标准图 API 解不了，真正考验对图结构与算法的理解
	- 描述贴近 **真实场景**，更接近实际应用中的图问题
- 配套写了专门的转换程序，把测试用例整合进自然语言描述、统一输入输出格式，对齐 §2 的图推理问题定义

---
## 3.3 提出简单而强的基线 Simple-RTC

- **Simple-Reasoning-Then-Coding**：把图推理与编码 **解耦**，四步流水线——
	1. **Formatting**：抽取无数据的问题描述 + 标准化输入输出要求（few-shot 提示）
	2. **Extracting**：用正则按标准输入要求从原题提取数据
	3. **Reasoning**：核心步，只专注 **设计算法/伪代码**，不被图数据干扰
	4. **Coding**：把伪代码翻译成可执行代码，处理提取的数据得最终答案
- 关键设计：推理只产出算法描述/伪代码（封装核心逻辑、数据结构、解题步骤），交给高效编码 LLM 实现，规避了强推理模型反复生成代码的高成本；且同类问题的正则/算法/代码 **可复用**，大幅提效

> [!success] 效果与意义
> - 旧基准上 **近乎满分**，较基座 GPT-4o-mini 平均提升 **~48%**（各基准 39%~62%），GraphArena 的 NP-hard 任务（如 TSP 用状态压缩 DP）提升尤其显著，且大图上提升比小图更明显（语言类对图规模敏感，Simple-RTC 扩展性强）
> - 新 GraphAlgorithm 上仅 **33.7%**，但显著超过所有对手（GraphTeam 8.7%、GCoder 3.0%、GraphWiz 0.0%），既证明方法有效、也证明新基准确有挑战
> - 换更强推理模型做 Reasoning 步：33.7%（GPT-4o-mini）→ 57.6%（o3-mini-high）→ 62.0%（DeepSeek-R1），坐实 **推理能力是图推理的核心瓶颈**
> - 作为一个 **不做专门训练** 的强基线，为后续"提升图推理专项能力"的研究立了标尺

# 四、方法与模型

Simple-RTC（Simple-Reasoning-Then-Coding）的核心思想是 **解耦推理与编码**，模仿图专家解题方式：先专注分析问题、设计算法，再用代码精确执行海量操作。整个流水线分四步，且四步都围绕统一的 **Problem Formulation（问题表述）** 协同
## 4.1 Formatting（格式化）

针对"LLM 记不住复杂图结构、且大量描述图的 token 会干扰对问题本身的分析"这一痛点：

- 从原题中抽取 **去数据化的问题描述**，并给出标准化的输入/输出要求（即 Problem Formulation）
- 双重作用：一是让后续推理 **聚焦于图问题分析与算法设计**，不被具体数据干扰；二是把提取的数据、推理产出的算法、编码产出的代码统一对齐到同一套输入输出规范下
- 用 **few-shot 提示** 引导（prompt 见附录 B.1）

---
## 4.2 Extracting（提取）

- 在得到 Problem Formulation 后，指示 LLM **用正则表达式** 按标准输入要求从原题中提取数据，转成标准输入格式（prompt 见附录 B.2）
- 关键细节：用正则而非直接复制（不同题数据不同）；节点名含空格时替换为 `_`、含 `.` 时特殊处理，去掉示例边等，避免读取歧义

---
### 4.3 Reasoning（推理）—— 核心步

这是解决复杂图推理问题的关键，也是焦点转向所在：

- **不让模型复刻算法执行轨迹，只让它设计算法**。输入是格式化得到的标准化问题表述（不含图数据），输出是 **算法描述或伪代码**
- 设计动机：
	- Prograph 实验表明，LLM 直接生成代码解图问题时一次成功率低、各种执行报错
	- 强推理模型（如 DeepSeek-R1）处理复杂问题耗时长，反复调用做代码生成成本极高
	- 但强推理模型的核心成果可以 **存成算法描述/伪代码** —— 它封装了核心算法逻辑、关键数据结构、分步解题思路，足以指导后续更高效的编码 LLM
- 因此用 **强推理模型作为 Reasoning 步的基座**，专门负责算法设计（示例见附录 D.1，如 TSP 用状态压缩 DP）

---
## 4.4 Coding（编码）

- 用 **高效编码 LLM（如 GPT-4o-mini）** 生成代码
- 输入 = 推理步给的算法/伪代码 + 格式化步给的问题表述；输出 = 可执行程序，处理提取步得到的数据，按标准输出要求给出最终答案

---
## 4.5 关键设计：复用性

由于正则（Extracting）、算法（Reasoning）、代码（Coding）**全部基于同一个 Problem Formulation 设计**，同类型问题可以直接 **复用** 这些产物——无需对相同任务重复推理，大幅提升解题效率（详见附录 F 的效率实验，复用后单题时间从 23.89s 降到 0.27s）

> [!note] 形式化对比
> - 语言类方法：$M(G, Q) \to A$（直接出答案）
> - 代码增强类：$M(G, Q) \to C,\ \text{exec}(C) \to A$（出代码再执行）
> - Simple-RTC：把上式中的 $M$ 拆成 **Format → Extract → Reason（设计算法）→ Code**，让推理只负责算法设计、把精确执行交给代码

# 五、实验与结论（数据说明了什么、有什么局限性）

## 5.1 实验设置

- **基准**：旧基准选 NLGraph、Talk like a Graph（GraphQA）、GraphInstruct、GraphWiz、GraphArena 五个（其中修正了 GraphWiz 的 Hamilton Path、Subgraph Matching 错误测试集）；外加自建的 **GraphAlgorithm**（239 题 / 3,041 实例）
- **对比方法**：
	- 语言类：GPT-4o-mini、GraphWiz（取最优的 LLaMA2-13B-RFT）、各基准上的 Previous SOTA
	- 代码增强类：GraphTeam、GCoder（取较优的 GCoder-Llama）
	- GraphTeam 与 Simple-RTC 均以 GPT-4o-mini 为基座

---
## 5.2 主要结果

### 5.2.1 旧基准：近乎满分

- Simple-RTC 五个基准平均排名 **1.0**，较基座 GPT-4o-mini 平均提升约 **48%**（各基准 39%~62%）
- 微调模型（GraphWiz、GCoder）只在自家训练集上好，换基准 **大幅退化**（GraphWiz 在 GraphArena 仅 2.4%，GCoder-L 仅 5.6%）
### 5.2.2 GraphArena：NP-hard 任务是分水岭

- Simple-RTC 在 NP-complete 任务上提升最显著（如 TSP，小/大图 **100.0 / 95.2**，远超基座的 31.8 / 0.0）
- 原因：推理焦点转向算法设计后，能设计出更高效的算法（TSP 用状态压缩 DP），在限定规模内（≤20 节点）解掉 NP-hard 题
- **大图提升比小图更明显**——语言类对图规模敏感（"重复迭代回溯"），而 Simple-RTC 扩展性强
### 5.2.3 GraphAlgorithm（新基准）：真正拉开差距

| 方法 | 平均准确率 |
|---|---|
| GraphWiz | 0.0% |
| GCoder-L | 3.0% |
| GraphTeam | 8.7% |
| GPT-4o-mini | 14.3% |
| **Simple-RTC** | **33.7%** |

- Simple-RTC 显著领先所有对手，但绝对值仅 33.7%，说明新基准 **确有挑战性**
- 依赖 API/知识库的 GraphTeam、GCoder 几乎全军覆没——因为这些题没有现成图 API，需要变形或新设计算法
- 微调的 GraphWiz 完全无法解未见过的问题（0.0%）
### 5.2.4 推理基座消融：推理能力是核心瓶颈

固定 Extracting/Coding，只换 Reasoning 步的基座：
- GPT-4o-mini **33.7%** → o3-mini-high **57.6%** → DeepSeek-R1 **62.0%**
- 慢思考（slow-thinking）模型提升尤其大
### 5.2.5 效率

- 大图最短路上 Simple-RTC 扩展性远好于 GPT-4o（200 节点：34.6s vs 207.7s）
- 同类问题复用代码后单题时间 23.89s → **0.27s**、成本 $0.0257 → $0.0020

> [!success] 数据说明了什么
> 1. **基座模型被低估**：不改模型、不做训练，仅把推理焦点从"复刻算法"转为"设计算法 + 写代码"，GPT-4o-mini 性能就大幅跃升——证明瓶颈在 **用法（推理焦点）**，不在基座能力
> 2. **微调和 API 路线都是死路**：微调过拟合训练任务、API 路线绕开了图推理本身，二者在未见过的难题上几乎归零
> 3. **图推理能力是真瓶颈**：推理基座越强、性能越高，且新基准上最高也才 62%，说明"设计图算法"这件事本身还远未被解决

---
## 5.3 局限性

- **未对推理步做专门训练**：Simple-RTC 只是把现成强推理模型当基座，没有针对图问题去 **强化训练推理能力**——作者自己点明这是留给未来的核心方向
- **NP-hard 仅限小规模**：状态压缩 DP 之类的指数级算法只能在很小的图（如 TSP ≤20 节点）内奏效，规模一大依然不可行——本质是算法复杂度的硬限制，不是方法能绕过的
- **新基准绝对性能仍低**：33.7%（GPT-4o-mini 基座）说明对真正需要原创算法设计的难题，当前 LLM 远谈不上胜任
- **依赖编码与执行环境**：把图推理"外包"给代码执行虽然规避了语言复刻的崩溃，但也意味着 **它评测的是"能否设计出可被代码实现的算法"，而非模型在图文本上原生的结构推理**——某种意义上回避了"模型是否真在图上推理"这个问题

> [!abstract] 结论
> 现有 LLM 图推理方法与基准都存在问题：基座模型因用法不当被低估。把推理焦点改为"设计算法"后，基座模型即可解掉旧基准大部分任务。本文构建更难的 GraphAlgorithm 基准，并提出简单而强的 Simple-RTC 基线。未来工作聚焦于 **专门提升 LLM 的图问题推理能力**，让模型真正学会理解图结构、分析图问题、设计图算法

# 六、关联课题需求（该文献的方法能否解决我的实验痛点、其缺陷是否可通过我的方案弥补）

> 我的课题：**Graph-Intervention Faithfulness（GIF）**——诊断 LLM 在图推理时是真正"跟随图结构"，还是在利用图文本序列化中的位置启发式（终点锚定等）。核心指标 Raw GIS / PC-GIS / GFI / POR / EAR
## 6.1 该文献的方法能否解决我的实验痛点

**基本结论：不能，而且方向上正交甚至相反。**

- **它解决的是"做对"，我研究的是"为什么对"**。Simple-RTC 的全部努力是把图题的答案准确率提上去，手段是 **把推理外包给符号执行**（Reasoning 出伪代码 → Coding 出代码 → 执行得答案）。我的痛点恰恰是：当模型声称"在跟随图"时，它到底是真在图上推理，还是序列化位置锚定。Simple-RTC 根本不碰这个问题

- **它的 pipeline 会直接抹掉我要测的现象**。GIF 的关键操作是构造反事实图 G1/G2 + 四种位置控制序列化版本，观察答案/CoT 是否随图结构变化。而 Simple-RTC 的 Formatting 步会 **抽取去数据化的问题描述、把图数据剥离出推理过程**——这等于人为消除了"图文本如何被序列化、节点出现在什么位置"这一变量。一旦图被正则提取成结构化标准输入交给代码处理，EAR（终点锚定率）、PC-GIS 这些指标就失去了测量对象

- **它默认了我要质疑的前提**。Simple-RTC 隐含假设"LLM 在长图文本上原生推理本就不行，所以别让它做"。我的工作是去 **量化这种"不行"到底是能力缺失还是位置投机**——这是它跳过的诊断步骤

一句话：**Simple-RTC 是一个工程化的"绕过方案"，而 GIF 是一个诊断性的"显微镜"。它没法当我的方法用，但可以当我的"反面参照"**

---
## 6.2 它的缺陷是否可通过我的方案弥补

**可以，而且这正是把它写进 related work 的最佳角度。**

- **缺陷一：用"答案准确率"掩盖了推理真实性问题。** Simple-RTC 在旧基准近乎满分、GraphArena 大涨，但这套数字完全无法区分"模型真理解了图结构"和"代码替它算对了"。我的 GFI = Raw GIS − PC-GIS 恰好就是为戳破这种 **"图推理虚胖"** 设计的——Simple-RTC 的高分本质上是把虚胖问题外包掉了，而非消除了。**我的方案能给它的高分提供一个 faithfulness 维度的"折扣率"度量**

- **缺陷二：它自己承认"没对推理步做专门训练、推理能力是真瓶颈"，却没有诊断工具。** 论文用"换更强推理基座（33.7%→62%）"来证明推理重要，但这只是把准确率当推理能力的代理指标。**我的 GIF 框架能更精细地回答"强推理模型强在哪"**：是真的更跟随图结构（PC-GIS 上升、GFI 下降、decoy-last 的 EAR 归零），还是只是位置鲁棒性更好。我的 Pilot 结果已经显示，提示形式（要求显式输出路径，类似它的 Reasoning 步输出伪代码）能把 decoy-last EAR 从 100% 压到 0%——**这恰好为"为什么 Reasoning-Then-Coding 有效"提供了一个机制层面的解释**：它的有效性可能部分来自"强制显式化中间结构、压制了位置锚定"，而不全是"算法设计能力"

- **可借用的点**：它的 GraphAlgorithm 基准（竞赛题、需原创算法、描述真实化）证明了"经典图基准太简单、有记忆泄漏"。我的 GIF 用 BFS/DFS 符号程序验证 gold path 唯一性的反事实图构造，同样是在对抗"记忆造成的虚胖"——只是 CofCA 抓记忆虚胖、我抓序列化位置虚胖。**它可以作为"基准必须更难才能暴露真实能力"这一论点的同盟证据**

> [!important] 定位结论
> Simple-RTC 与 GIF **正交且互补**：它用工程手段把图推理外包给代码、回避了"模型是否真在图上推理"的问题；我的 GIF 正是把这个被回避的问题 **量化成可测指标**。在 related work 中，它最适合作为 **"主流提升路线如何系统性绕开 faithfulness 问题"** 的代表——既反衬出我课题的必要性，又为"显式化中间结构能压制位置锚定"这一机制猜想提供了一个间接的外部佐证

> [!note] 可写进论文的一句话
> "近期提升路线（如 Simple-RTC, Hu et al. 2025）通过将图推理解耦为算法设计 + 代码执行来提升准确率，但这恰恰把'模型是否真正遵循图结构'的问题外包给了符号执行而非加以验证；本文的 GFI 指标正是为填补这一诊断空白而设计"
