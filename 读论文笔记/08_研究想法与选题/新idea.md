## 第一：缺少时空尺度分析

低轨卫星网络有不同时间尺度：

|系统部分|时间尺度|
|---|---|
|物理层 / MAC 调度|毫秒级|
|路由变化|秒级|
|业务流量变化|分钟级|
|轨道周期规律|小时级|
|LLM 推理|秒级到十几秒|

这里有一个天然矛盾：

> 大模型思考太慢，但网络变化可能很快。

所以不是所有事情都能交给 LLM。

比如：

- 毫秒级调制编码选择，不适合 LLM；
- 秒级路由决策，可能需要小模型或强化学习；
- 分钟级任务规划，可以让 LLM 参与；
- 小时级运维分析、故障总结、策略生成，更适合 LLM。

这就能形成一个很强的论文主线：

> **多时间尺度 AI 协同。**

这个比单纯说“LLM + 卫星”高级很多。

## 方向二：星座级分布式知识一致性

这是 RAG 和低轨卫星结合最自然的地方。

普通 RAG 是：

> 用户问问题 → 去数据库检索 → LLM 回答。

但低轨卫星环境下，知识库不可能像云服务器那样稳定。

它会遇到：

- 卫星之间连接断断续续；
- 星间链路带宽有限；
- 每颗星存储有限；
- 地面站连接窗口有限；
- 不同卫星看到的状态不一样；
- 知识更新可能不同步。

所以问题变成：

> 星座里的 RAG 知识怎么分布、缓存、更新、同步？

这比普通 RAG 有卫星特色。


## 方向三：因果推理故障诊断

这是最像“能单独成论文”的方向。

可以这样理解：

普通故障诊断是：

> 看到异常 → 判断可能故障。

因果故障诊断是：

> 建立故障因果图 → 推断根因 → 给出干预策略。

比如：

```
太阳翼异常 → 电源下降 → 通信模块功率不足 → 链路质量下降
```

或者：

```
姿态偏差 → 天线指向误差 → 信号强度下降 → 数据重传增加
```

这种因果链对卫星很重要，因为卫星故障不能乱修，必须知道根因。

AI 认为这比泛泛讲“LLM 调度”更有学术价值。
