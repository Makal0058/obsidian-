# 一、研究背景（前人做到哪一步）
## 1.1 传统卫星路由方法

早期 LEO 卫星网络主要采用传统路由算法，例如最短路径、负载均衡、基于链路状态的动态路由、SDN 路由。

注：
- 最短路径：从起点到终点，找“代价最小”的那条路。“代价”可以是距离最短、传播时延最低、跳数最少。
- 负载均衡：同时关注路径最短与路径不堵，目的是**不要所有数据都挤在少数几条链路上**。
- 基于链路状态的动态路由：网络状态变了，路由也跟着变，或者链路虽然没断，但拥堵程度变化，也可以重新计算路径。“动态”强调的是**根据实时网络状态不断更新路由。**
- SDN 路由（软件定义网络）：特点是**把“控制”和“转发”分开。**

中央控制器：负责思考路线  
           ↓  
各个交换机/卫星：照着规则转发

缺点是 LEO 星座规模很大，中央控制器收集全局信息的通信开销和响应延迟可能很高。
## 1.2 引入 DRL 做逐包路由

典型思路是每颗卫星作为一个 Agent 收到一个数据包 $\to$ 用 DNN 根据当前状态做一次推理 $\to$ 选择下一跳卫星

比较适合大规模 LEO 网络，也能动态适应网络状态变化。

已有工作甚至已经使用 DQN、MADRL、GNN + DRL、POMDP 进行动态下一跳选择。

注：
- DQN（深度 Q 网络）：输入当前网络状态，输出每个候选下一跳的 Q 值。用神经网络来学现在应该把包转给谁。
- GNN（图神经网络）+ DRL：**GNN 负责理解网络结构，DRL 负责做决定。**
- POMDP：**对决策问题的数学建模方式**。每颗卫星看不到整个网络的真实全局状态，只能看到自己附近的一部分状态。然后根据这部分 observation 选择下一跳。
## 1.3 已有 flow routing 主要采用集中式架构

不是对每个 packet（数据包）单独做决策，而是针对整个 traffic flow（数据流）选择路径。这种 flow routing（按“数据流”来决定路由）可以减少重复路由决策，但已有 DRL flow routing 大多依赖中央 SDN Controller（软件定义网络控制器）。中央节点获取全局网络状态，然后统一决定整条 flow 的路径。

LEO 卫星网络规模很大，集中式方法会带来较高通信开销、较大的控制响应延迟、可扩展性不足，并不完全适合大型 LSBN。
## 1.4 已有工作的主要不足

这篇论文认为前人最关键的问题是**忽略了 DNN inference time，也就是神经网络推理本身需要时间。**

以前很多 DRL 路由论文默认**数据包一到 $\to$ 神经网络立刻给出路由结果**。但实际 LEO 卫星算力有限，而激光星间链路的数据转发速度非常高。

如果数据包到达速度 > DNN 推理速度，就会出现数据包等待推理、决策队列越来越长、延迟增大、缓存满、丢包、吞吐量下降。
## 1.5 这篇论文真正要补的 gap

**现有 packet-centric DRL 每个数据包都进行一次 DNN 推理，推理速度可能成为高吞吐 LEO 网络的瓶颈；而已有 flow-centric DRL 又多数依赖集中式架构，缺乏适用于大规模 LEO 网络的全分布式 flow routing 方法。**

# 二、创新点与贡献
## 2.1 首次系统关注 DNN 推理时间对卫星 DRL 路由的影响

以往很多 DRL 路由工作默认数据包一到 $\to$ DNN 立刻完成推理 $\to$ 马上决定下一跳，但本文指出，这个假设在高吞吐 LEO 网络里并不现实。

注：DNN（深度神经网络）推理就是**把当前输入丢进已经训练好的深度神经网络里，让它算出一个输出。**

由于星上算力有限，而激光星间链路的数据转发速度很高，如果数据包到达速度 > DNN 推理速度，就会产生决策排队 $\to$ 时延增加 $\to$ 缓存溢出 $\to$ 丢包 $\to$ 吞吐量下降。

作者不仅指出这个问题，还专门通过实验和定量分析证明 DNN inference time 会显著影响 DRL 路由性能。
## 2.2 提出全分布式的 Flow-Centric DRL 路由方法

这是这篇最核心的创新。

传统 packet-centric DRL 对每个 packet 都执行一次 DNN 推理；本文改成**每个 traffic flow 只对第一个 packet 做一次 DNN 推理。**

将结果保存到 Flow Routing Table，后续属于同一个 flow 的 packet 直接查表转发，不再运行 DNN。

这样就把一包一推理改成**一流一推理**，从而显著减少累计 DNN inference time，提高路由吞吐量。
## 2.3 重新设计适合 LEO 网络的 Traffic Flow 定义

如果按照传统同一个源用户 + 同一个目的用户 = 一个 flow，那么 LEO 网络面向全球海量用户，source-destination 组合可能非常多，flow 数量会爆炸。

所以作者专门重新定义 flow，**对于每颗卫星，从同一个网络端口进入，并且目标是同一颗目的 LEO 卫星的一系列连续 packet，被认为属于同一个 flow**，这样可以大幅减少每颗卫星需要维护的 flow 数量。
## 2.4 采用全分布式 MADRL，而不是依赖中央 SDN Controller

已有很多 DRL flow routing 方法依赖 SDN Controller（中央控制器）掌握全局状态，然后统一给 flow 规划完整路径。

即

本文则采用 **Fully Distributed Architecture**（完全分布式架构），每颗 LEO 卫星都是独立 Agent，只根据自己的局部 observation 决定当前 flow 下一跳应该发给哪颗邻星，并将问题建模成 POMDP。
## 2.5 提出自适应 Flow 路由更新机制

Flow routing 有一个明显问题，假设第一个 packet 来时算出 A $\to$ B $\to$ C，后面的 packet 都沿用这条路线。

但 LEO 网络一直在变化，卫星运动、链路断开、网络负载变化、拥塞状态变化。原来保存的 flow route 过一段时间可能就不再合适了。

因此作者又增加一个 **Adaptive Flow Routing Updating Scheme**（自适应流路由更新机制），根据感知到的 delay jitter（时延抖动）判断什么时候需要更新 flow route。

# 三、实验与结论（数据说明了什么、有什么局限性）

## 3.1 实验比较了哪些方法

作者设置了两个场景：类 Iridium 的 LEO 卫星网络、更大规模的 LSBN（低轨卫星宽带网络），并与四种 baseline 比较：

- OSPF：按最短路径查路由表转发，**只管“哪条路最短”，不太管哪条路现在堵不堵。**
- HeurOSPF：在 OSPF 基础上优化链路权重，哪条路又合适又不太堵就走哪条。
- ELB（显式负载均衡）：专门面向卫星网络设计的负载均衡路由，核心想法是不要让某些卫星/链路特别忙，而其他地方很闲。
- Packet-Centric DRL：每个 packet 都单独执行一次 DNN 推理来决定下一跳

同时测试本文 Flow-Centric DRL 在不同 delay-jitter 阈值 $\theta_{thr}=0.001,0.005,0.008$ 下的表现，主要评价端到端时延、丢包率、单颗卫星吞吐量、整个网络吞吐量、平均路由决策时延 ADD。

注：
- **端到端时延（End-to-End Delay）**：一个 packet 从源卫星出发，到达目标卫星总共花了多久。里面包括决策排队、DNN 推理、转发排队、传输和传播时间。**越小越好**。
- **丢包率（Packet Loss Ratio）**：所有发送的数据包里，有多少包因为队列满、处理不过来等原因被丢掉。比如 1000 个包丢 20 个，就是 2%。**越低越好**。
- **单颗卫星吞吐量（Satellite Throughput）**：一颗卫星单位时间内实际能成功转发多少数据。可以理解为“这颗卫星每秒能扛多少流量”。**越高越好**。
- **整个网络吞吐量（Network Throughput）**：整个 LEO 卫星网络单位时间内总共能成功传输多少数据。它看的是全星座整体的数据承载能力。**越高越好**。
- **平均路由决策时延（ADD, Average Decision Delay）**：一个 packet 平均要等多久才能得到“下一跳该去哪”的路由决定。对 Packet-Centric DRL 来说，这里面很大一部分就是 DNN 推理和等待 DNN 推理的时间。**越小越好**。
## 3.2 Flow-Centric DRL 大幅降低了 DNN 决策时延

这是全文最关键的实验结果。在用户数量较大时，传统 Packet-Centric DRL 的平均决策时延达到类 Iridium 场景：42.9 ms、大规模场景：51.9 ms；而 Flow-Centric DRL 可以降到大约 1 ms、3 ms。

也就是说，逐包 DNN 推理原本甚至会占到总端到端时延的一半以上，而改为按 flow 推理之后，决策时延占比被压到很低。

这直接证明了本文最核心的判断：高吞吐 LEO 网络中，DNN inference time 不是可以忽略的小开销，而可能成为真正的路由瓶颈。
## 3.3 Flow-Centric DRL 提高了整体网络吞吐量

由于大量后续 packet 不再重复执行 DNN，而是直接查 flow routing table，卫星可以更快转发数据。

实验中，本文方法使整个网络吞吐量达到约类 Iridium 场景：64 Gb/s、大规模场景：118 Gb/s，并超过所有 baseline。

所以数据说明“一个 flow 只做少量 DNN 推理”确实能够释放路由器的处理能力，使整个 LEO 网络承载更大的流量。
## 3.4 同时降低端到端时延和丢包率

作者在两个场景中发现，Flow-Centric DRL 在 end-to-end delay、packet loss、network throughput 等指标上整体优于对比方法。
## 3.5 Adaptive Routing Update 确实有必要，但阈值不能乱设

Flow routing 的问题是前面决定好的路线可能随着卫星移动和网络负载变化而过时，所以作者用 delay jitter 决定什么时候重新调用 DNN 更新路线。

实验发现：

- 阈值太大：更新太慢，旧路线不能及时适应网络变化
- 阈值太小：更新太频繁，又会重新产生大量 DNN inference

比如在类 Iridium 场景中，$\theta_{thr}=0.005$ 表现优于 0.001 和 0.008；但在更大规模网络中，0.008 又略优于 0.005。

这说明“**多久重新算一次路由”本身存在一个性能权衡，而且合适的阈值与网络规模有关**。
## 3.6 最终结论

论文最终认为 Flow-Centric DRL 通过将路由决策粒度从单个 packet 改为整个 traffic flow，大幅减少 DNN inference 次数；同时采用完全分布式架构以及自适应路由更新机制，使其能够适应大规模、高动态、高吞吐的 LEO 卫星网络。

实验表明，该方法在端到端时延、丢包率、网络吞吐量、平均决策时延等指标上总体优于 baseline。
## 3.7 局限性

1. **网络模型还不够高保真**

论文自己明确提出，未来还需要在更复杂、更高保真的 LSBN 星座配置中继续验证方法，所以目前的仿真仍然是经过简化的卫星网络环境。

2. **星上 DNN 推理能力仍然是现实约束**
j
本文通过减少 DNN inference 次数缓解问题，但并没有让星载计算能力这个限制消失。作者自己提出，未来希望把 Flow-Centric DRL 和 NPU 等硬件加速器结合，以进一步提高卫星吞吐能力。

所以本文主要从“路由算法层面”减小推理开销，硬件加速仍然是后续方向。

3. **更新阈值需要针对场景选择**

实验已经表明不同网络规模下，最合适的 $\theta_{thr}$ 不一样，小了会频繁推理，大了又会更新不及时。

所以当前方案仍然存在**阈值如何自适应选择**这个问题，论文目前主要测试几个预先给定的阈值，并没有证明存在一个对所有场景都最优的固定值。
