# 一、研究背景（前人做到哪一步）

低轨卫星宽带网络 LSBN 与边缘计算结合后，卫星不仅负责通信，也可以直接处理地面用户产生的计算任务。这样可以减少任务全部传回地面云端带来的时延和带宽开销。

注：
- **LSBN（低轨卫星宽带网络）**：由很多低轨卫星组成的宽带通信网络，作用类似“天上的互联网基站”，给地面用户提供网络接入，尤其适合偏远地区。论文里提到 Starlink 这类系统就是典型例子。

- **边缘计算（Edge Computing）**：把计算任务放到“离用户更近的地方”处理，而不是全部传到很远的云服务器。论文里这里的“边缘节点”就是低轨卫星本身：卫星带有一定计算资源，可以直接处理用户任务，从而减少传输时延和网络带宽消耗。
## 1.1 前人主要发展了两条路线

1. **传统优化方法**  

   已经有人使用博弈论、匹配理论、ADMM、拉格朗日分解等方法，联合优化计算卸载和资源分配 JCORA。  
   
   但这些方法通常需要多次迭代求解，在 LEO 卫星网络这种高速移动、拓扑不断变化的环境里，很难满足实时决策要求。

2. **DRL 方法**  

   后来研究者开始用 DRL 做卫星计算卸载和资源分配，因为训练完成后，DNN 可以快速给出决策，更适合动态环境。已有工作已经使用 PPO、MADRL、Actor-Critic 等方法解决相关问题。

## 1.2 已有 DRL 工作的问题

1. 已有 DRL 工作有一个核心问题，**计算卸载和资源分配本质上属于两种不同类型的动作。**

计算卸载是离散动作，例如：本地算 / 给上面卫星 / 给下面卫星 / 左边 / 右边 / 云端；资源分配是连续动作，例如：给这个任务分配 1.2 GHz、2.5 GHz 还是 3.1 GHz 的计算资源。这就形成了**Discrete + Continuous = Hybrid Action Space（离散—连续混合动作空间）**，大多数传统 DRL 算法并不擅长直接处理这种混合动作空间。

前人主要有三种处理方式：

- 只研究卸载 → 只处理离散动作  
- 只研究资源分配 → 只处理连续动作  
- 把连续动作离散化，或者把离散动作连续化 → 强行变成同一种动作空间

但论文认为，前两种没有真正联合优化 JCORA（联合计算卸载与资源分配）；后一种又容易产生扩展性、近似误差和泛化问题。还有工作直接用规则公式完成资源分配，虽然绕开了混合动作空间，却降低了算法的智能化程度。

2. 系统层面的问题，**卫星负载严重不均衡**。

大约 70% 的 LEO 卫星因为飞过人口稀少地区而没有被充分利用，而人口密集地区上空的卫星反而可能非常拥堵。以前的很多架构没有充分利用卫星之间的 ISL（星间链路），把任务转给附近空闲卫星。

所以这篇论文面对的是两个主要缺口**卫星之间算力利用不均衡**、**JCORA 存在难处理的离散 + 连续混合动作空间**。然后作者提出多级卫星协同计算架构 + HMADRL，把问题拆成：

- 上层：MADDQN 做离散的计算卸载  
- 下层：DDPG 做连续的资源分配。

# 二、创新点与贡献

1. **提出多级边缘计算架构，利用邻星协同缓解负载不均衡**

作者不是让任务只能在“接入卫星”和“地面云”之间二选一，而是允许任务接入卫星 $\to$ 邻近卫星 $\to$ 更下一层邻星 $\to$ 最后某颗卫星处理，或者送到云端。

这样就能利用 ISL，把繁忙卫星上的任务转移给附近比较空闲的卫星，从而提高整个星座的算力利用率和负载均衡。

2. **提出 HMADRL，把混合动作空间拆成两层分别处理**

JCORA 同时包含计算卸载（离散动作）、资源分配（连续动作），作者没有强行把它们放进一个统一动作空间，而是采用 divide-and-conquer：

- 上层 GCO：决定任务去哪里 $\to$ MADDQN  
- 下层 LRA：决定分多少计算资源 $\to$ DDPG

这样就绕开了传统 DRL 难以处理离散+连续混合动作空间的问题。

3. **为上层卸载设计 delayed reward，并采用 CTDE**

一个任务可能经过好几颗卫星才能最终完成，因此前面某颗卫星做出“继续转发”的动作时，马上并不知道这个决定到底好不好。

所以作者不是立刻给 reward，而是等任务最终处理完成，再把后续产生的传输和计算代价反馈给之前参与卸载决策的卫星。这样前面的 Agent 能根据任务最终结果学习，而不是只看眼前这一跳。

同时 MADDQN 使用 centralized training + distributed execution（集中训练 + 分布式执行）：训练时可以利用集中反馈，实际运行时每颗卫星只根据自己的局部观测做决策。

# 三、实验与结论（数据说明了什么、有什么局限性）
## 3.1 实验

作者在类 Iridium 的 LEO 星座中进行仿真，66 颗卫星，6 个轨道面，每个轨道面 11 颗卫星；活跃用户数量为 7000～19000；单颗卫星计算资源在 2.4～4.8 GHz 范围内变化。

仿真使用 STK 模拟卫星运动和动态拓扑，Python 模拟任务生成、传输和计算，PyTorch 实现 HMADRL（分层多智能体深度强化学习）。

主要评价三个指标：

- ATPD：平均任务处理时延，越低越好
- OR：任务超出规定时限的比例，越低越好
- LBI：负载均衡指数，越高表示各卫星负载越均衡

作者将 HMADRL 与 Greedy、Random、Cloud Computing、C-DRL、D-DRL 5 种方法比较，实验结果主要说明三件事：

注：
- Greedy：贪心法。任务直接在离用户最近的接入卫星上处理，而且把可用计算资源尽量给它。优点是简单、近；缺点是用户一多，接入卫星容易堵。
- Random：随机法。卫星收到任务后，随机选卸载位置和资源分配方案。主要就是当一个“很弱的下限基准”。
- Cloud Computing：全云计算。所有任务都通过卫星链路送到远端地面云处理。云算力强，但通信距离长，所以时延可能很大。
- C-DRL（连续化 DRL）：把原本离散的卸载动作，比如“本地/左/右/云端”，强行改成连续形式，再让 DRL 处理。问题是容易造成函数逼近和泛化困难。
- D-DRL（离散化 DRL）：反过来，把原本连续的资源分配，比如 2.37 GHz，切成几个固定档位，再让 DRL 选。问题是会损失精度，而且档位越细，动作空间越大。

1. **HMADRL（分层多智能体深度强化学习）能稳定训练**

当 learning rate = 0.01、batch size = 128 时，大约经过 230 个 episode 后 reward 收敛。学习率过大容易震荡，过小则收敛较慢。

2. **HMADRL 的任务处理性能最好**

总体上，HMADRL 在 ATPD 和 OR 上优于所有 baseline。

DRL 类方法相比 Cloud Computing、Greedy 和 Random，ATPD 分别降低约 31%、49%、51%，OR 分别降低约 52%、73%、71%。

在 DRL 方法内部：

- D-DRL 把连续动作离散化，会丢失精度并导致动作空间过大；  
- C-DRL 把离散动作连续化，会增加函数逼近和泛化难度；  
- HMADRL 则直接把离散卸载和连续资源分配拆开处理，因此效果更好。

3. **多级卸载确实改善了负载均衡**

用户只有 7000 时，超过 80% 的任务直接在接入卫星完成。

用户增加到 19000 后，接入卫星变得拥堵，此时不到一半的任务直接本地完成，超过 30% 的任务被卸载到两层以上的邻近卫星，LBI 提升到约 0.7。

这说明网络不拥堵时，没必要乱转任务；网络拥堵时，HMADRL 会主动利用邻近空闲卫星的计算资源。
## 3.2 结论

1. 利用 ISL 进行多级邻星协同卸载，可以缓解 LEO 卫星之间的负载不均衡。

2. 把 JCORA 拆成“离散计算卸载 + 连续资源分配”两层，再分别使用 MADDQN 和 DDPG，比把混合动作空间强行全部离散化或连续化效果更好。

因此 HMADRL 在平均任务处理时延 ATPD、任务超时率 OR、负载均衡 LBI 这三个主要指标上总体优于对比方法。
## 3.3 局限性

论文目前主要还是仿真实验，主要验证的是类 Iridium 星座场景。

作者自己在结尾提出，下一步需要验证 HMADRL 在其他场景中的适应能力，例如智能交通、UAV 辅助边缘计算等。
