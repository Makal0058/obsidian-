# 一、研究背景（前人做到哪一步）

1. **单层 LEO 卫星边缘计算**

早期研究主要关注 LEO 卫星自身的任务卸载和资源分配，例如：

- 决定任务是在本星计算还是卸载到其他 LEO；
- 联合优化计算资源与通信资源；
- 常用 ADMM、联合优化等传统优化方法。

但这类工作大多只考虑 LEO 单层网络，没有充分利用 GEO 卫星和地面云的计算资源。

2. **GEO–LEO–Cloud 多层协同**

之后研究开始把 GEO、LEO 和地面云结合起来：

- LEO：负责接入和边缘计算；
- GEO：提供更稳定、较强的计算能力；
- Cloud：提供近乎充足的计算资源。

已有工作证明，多层协同可以缓解 LEO 资源不足和过载问题。

但多数方法仍依赖启发式算法或凸优化，而且经常把 GEO / Cloud 当作静态、理想化资源，没有充分考虑链路和资源随时间变化的问题。

3. **DRL / 多智能体 DRL 开始用于动态决策**

近年来，研究者开始使用 DRL 和 MADRL 处理卫星网络中的：

- 任务调度；
- 任务卸载；
- 资源分配；
- 多卫星协同。

原因是卫星网络具有动态拓扑、随机任务到达和高维状态，传统优化方法难以实时求解，但现有 DRL 方法仍主要面向：

- 单层或同构网络；
- 单一类型动作。

注：
- 单层网络：就是只研究一层卫星网络，比如只研究 LEO 卫星，不考虑 GEO 和地面云。
- 同构网络：网络里的节点性质基本类似，比如全都是 LEO 卫星，算力差不多、链路类型差不多、能耗模型差不多；而这篇是异构网络，LEO、GEO、Cloud 三种节点完全不同，LEO 算力有限、能量有限、GEO 算力更强，但可能排队，Cloud 算力几乎无限。

**还没有很好解决一个关键问题**：在 GEO–LEO–Cloud 多层网络中，同时处理“离散的任务卸载决策” + “连续的计算资源分配”。

# 二、创新点与贡献

## 2.1 提出 GEO–LEO–Cloud 三层协同空间算力网络架构

论文把 LEO 卫星 + GEO 卫星 + 地面云统一到一个协同计算框架里。

其中 LEO 负责终端接入、任务转发和部分本地计算、GEO 提供更稳定、更强的计算能力、Cloud 提供大规模计算资源。

这样可以缓解单纯依赖 LEO 时的算力不足和负载不均问题。
## 2.2 联合建模任务卸载与资源分配

同时考虑任务卸载 + 计算资源分配，优化目标同时包括降低任务时延、降低任务失败率、降低 LEO 能耗、提高负载均衡。

将这些目标统一成一个多目标优化问题。
## 2.3 解决“离散 + 连续”的混合动作空间问题

这是这篇最核心的算法创新。

任务卸载是离散动作，例如本地 / 邻居 LEO / GEO / Cloud，而资源分配是连续动作，例如给任务分配多少 CPU 频率。

作者没有把两类动作硬塞进一个 DRL 网络，而是拆成两层。MADDQN 负责全局任务卸载，TD3 负责本地连续资源分配，从而降低混合动作空间带来的训练难度。

注：强化学习算法，MADDQN 擅长“从几个选项里选一个”、TD3 擅长“输出一个连续数值”。
## 2.4 提出分层 HA-MADRL 框架

每颗 LEO 都被看作一个智能体，内部包含两个模块:

- GTO 决定任务往哪里走
- LRA 决定本地分多少计算资源

而且两层之间不是完全独立的。

LRA 会把优化后的本地执行代价反馈给 GTO，让上层卸载策略知道“这颗卫星现在资源够不够、把任务送过去划不划算“，因此形成一个闭环反馈结构。
## 2.5 在 Starlink 和 OneWeb 场景中进行验证

实验结果表明，HA-MADRL 相比基线方法能够降低任务时延、降低能耗、降低任务失败率、改善 LEO 卫星之间的负载均衡。

论文是在 Starlink 和 OneWeb 配置下进行仿真验证的。

# 三、实验与结论（数据说明了什么、有什么局限性）
## 3.1 实验设置

1. **作者搭建了高保真仿真平台**

- 用 STK 模拟卫星轨道和拓扑；
- 用 Python 离散事件环境模拟任务生成、卸载和处理；
- HA-MADRL 用 PaddlePaddle 实现；
- 测试了两种大规模星座：
    - Starlink：1584 颗 LEO，72 个轨道面，550 km；
    - OneWeb：648 颗 LEO，18 个轨道面，1200 km；
- 另外配置 3 颗 GEO 和 10 个地面云网关；
- IoT 终端数量从 7000 增加到 19000，用来测试不同负载。
## 3.2 主要实验结果

1. **Starlink 场景：高负载下优势明显**

在 19000 个终端的重负载情况下：
- Greedy：
    - 平均时延 3.01 s
    - 失败率 27.72%
- Cloud-only：
    - 失败率高达 41.51%
- Random：
    - 能耗最高，为 63.21 kJ
    - LBI 只有 0.29

而 HA-MADRL 达到：
- 平均时延：1.34 s
- 失败率：6.77%
- 总能耗：41.89 kJ
- 负载均衡指数 LBI：0.69

说明 HA-MADRL 在高负载情况下能够同时控制时延、失败率、能耗和负载均衡，而不是只优化其中一个指标。

2. **系统会根据负载自动改变卸载策略**

轻负载时，Starlink 中约 78.11% 的任务在第一跳就直接执行，但当终端增加到 19000 个后第一跳执行比例下降到 35.38%，3～6 跳的多跳卸载比例增加到 40% 以上。

说明模型不是学了一个固定规则，而是会负载低 → 尽量本地算、负载高 → 主动把任务扩散到其他卫星，从而利用整个星座的闲置算力。

3. **OneWeb 场景证明了方法对不同拓扑有适应性**

OneWeb 的卫星更少、轨道更高，LEO 总计算资源只有 Starlink 的约 40%，因此资源更加紧张。

即便如此，HA-MADRL 仍然优于传统 DRL：

- 相比 C-DRL，平均时延降低约 7%；
- 相比 D-DRL，平均时延降低约 12%；
- LBI 达到 0.87。

而且随着 LEO CPU 能力从 2.4 GHz 提升到 4.2 GHz，能耗从 50.02 kJ → 26.04 kJ

说明算法会自动发现LEO 算力不足时，多卸载、LEO 算力变强以后，减少远距离卸载，多在本地执行。

4. **GEO 并不只是“中继站”，还能充当算力缓冲层**

在 19000 个终端、2.4 GHz 情况下：

|执行位置|Starlink|OneWeb|
|---|---|---|
|LEO|61.66%|47.74%|
|GEO|31.98%|44.90%|
|Cloud|6.36%|7.37%|

OneWeb 因为 LEO 更稀疏、更缺资源，所以有 44.90% 的任务交给 GEO。

这说明 GEO 在资源紧张时可以吸收 LEO 的过载任务，起到“算力缓冲层”的作用，而不仅仅是通信中继。

5. **混合动作分层优化确实比“硬合并”更有效**

作者还和两类传统处理混合动作的方法比较：

- C-DRL：把离散动作强行连续化；
- D-DRL：把连续资源强行离散化。

这两种方法都会引入近似误差或量化误差。

而 HA-MADRL：MADDQN 处理离散卸载、TD3 处理连续资源分配、两者通过 cost feedback 联系起来

实验结果整体更好，因此作者认为“先拆开、再通过反馈协调”比强行把离散和连续动作塞进同一个动作空间更合理。
## 3.3 局限性

论文自己明确承认的主要局限是 HA-MADRL 很依赖 LEO 卫星之间及时交换状态信息，MADDQN 做卸载决策时，需要知道邻居卫星当前的负载。

如果星间链路延迟很高、ISL 时断时续、邻居状态信息传过来时已经过期，模型看到的状态就不是最新状态，可能导致次优卸载决策。

另外还有一个实际问题：训练阶段本身计算复杂度较高，因为涉及大量智能体和混合动作空间；作者采用离线训练，所以认为这不会直接影响星上在线决策。在线推理阶段则比较轻量，TD3 Actor 只有 3 层全连接网络、每层 128 个神经元，推理延迟在毫秒级。

# 四、对我的启发

**“邻居状态过期、链路时断时续、不同节点看到的世界不一致”是分布式系统里的经典问题。** 🌿

比如 LEO A 想把任务卸载给 LEO B，但 A 看到的 B 的负载信息可能已经是 200 ms 前甚至更早的，分布式系统里会有几种典型办法：

- **时间戳 / 版本号**：状态带上“这是 t 时刻的数据”，太旧就不信。
- **TTL / bounded staleness**：规定状态最多允许旧到什么程度。
- **Gossip**：卫星之间不断把状态向邻居传播，不依赖一个中心节点。
- **心跳 / failure detector**：判断邻居是不是还在线、链路是不是已经失效。
- **预测**：不用“最后一次观测值”直接决策，而是根据历史状态预测“现在大概是什么状态”。
- **一致性协议**：像 Raft/Paxos 这类方法让多个节点对关键状态达成一致，但它们通信成本更高，在高速移动的 LEO 网络里未必适合每次卸载都做。

不过这里有个很重要的点，**不能简单说“加个 Raft 就解决了”**，因为 LEO 的问题特别，卫星高速运动 $\to$ 拓扑不断变 $\to$ ISL 可能断 $\to$ 状态变化很快 $\to$ 如果你为了强一致性一直等其他卫星确认 $\to$ 等一致了，状态可能又过期了 😭

所以卫星网络反而经常更适合**弱一致 / 有界过期 + 本地决策 + 状态预测 + RL**，而不是追求数据库那种“所有节点永远完全一致”。

例如你完全可以把这篇论文的局限改造成一个新问题：原论文假设邻居状态能及时获得，新工作主动引入 100 ms / 500 ms / 1 s 的状态延迟和丢包，研究 HA-MADRL 怎么退化，再加入 timestamp、状态预测或 world model，看看能不能恢复性能。
