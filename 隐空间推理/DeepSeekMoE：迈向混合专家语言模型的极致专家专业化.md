# 一、研究背景
## 1.1 前人做到哪一步

随着大语言模型参数规模不断扩大，模型的训练与推理计算成本也显著增加。传统稠密模型（Dense Model）在处理每个 Token 时，都需要使用全部模型参数，导致计算开销随模型规模持续增长。为解决这一问题，研究者提出了混合专家模型（Mixture-of-Experts，MoE），通过稀疏激活机制，在扩大模型参数规模的同时控制计算成本。

**MoE 的核心思想是将 Transformer 中的前馈神经网络（FFN）替换为多个专家网络，并通过路由器为每个 Token 动态选择少量专家参与计算。** 其中，GShard 采用 Top-2 路由策略，Switch Transformer 采用 Top-1 路由策略。这些方法证明了稀疏激活架构能够在不显著增加单次计算量的情况下，提高模型容量与性能。

因此，已有研究基本解决了**如何通过稀疏激活扩大模型容量，同时控制计算成本**的问题。然而，专家数量的增加并不意味着不同专家就能自动形成明确且互补的知识分工。
## 1.2 现有方法的主要问题

尽管传统 MoE 架构已经取得显著进展，但作者认为，现有方法仍未充分实现专家专业化（Expert Specialization），即让不同专家分别掌握相对独立且集中的知识。论文主要指出两个问题。

**第一个问题是知识混杂（Knowledge Hybridity）。** 传统 MoE 通常只设置有限数量的专家，导致同一个专家需要处理涉及多种知识的 Token。例如，一个专家可能同时接收数学、编程和语言理解相关的输入，被迫在自身参数中学习多种不同类型的知识。这使得专家难以专注于特定知识，也难以同时有效利用这些知识。

**第二个问题是知识冗余（Knowledge Redundancy）。** 不同专家所处理的 Token 往往需要某些共同知识，例如基础语言知识。如果每个专家都独立学习这些共通知识，就会出现多个专家重复存储类似信息的现象，降低参数利用效率。

**这两个问题共同限制了 MoE 的专家专业化程度：一方面，单个专家需要学习过多种类的知识；另一方面，不同专家又可能重复学习相同知识。** 因此，传统 MoE 虽然能够扩大模型容量，却未必能够充分利用新增的专家参数。
## 1.3 本文的研究切入点

针对上述问题，本文提出 DeepSeekMoE，其核心研究思路是：**通过改进专家的组织方式与激活机制，提高专家专业化程度，使有限的参数与计算资源得到更有效的利用。**

首先，针对知识混杂问题，作者提出**细粒度专家划分（Fine-Grained Expert Segmentation）**。具体而言，将传统 MoE 中较大的专家拆分为更多、更小的专家，同时增加每个 Token 激活的专家数量。在保持专家总参数量和计算成本基本不变的前提下，使不同知识能够被更细致地分配给不同专家，并提高专家组合的灵活性。

其次，针对知识冗余问题，作者提出**共享专家隔离（Shared Expert Isolation）**。该方法将部分专家设置为始终激活的共享专家，用于集中学习不同输入共同需要的知识；其余专家则由路由器动态选择，使它们能够更加专注于特定知识，从而减少不同路由专家之间的重复学习。

**本文并不是单纯通过增加专家数量来提升模型性能，而是通过细粒度专家划分与共享专家隔离，改善专家之间的知识分工。** 作者希望由此提高 MoE 的参数利用效率，在相近计算成本下获得更好的模型性能。
# 二、创新点与贡献
## 2.1 细粒度专家划分（Fine-Grained Expert Segmentation）

传统 MoE 通常采用少量较大的专家，每个专家需要学习多种不同类型的知识，难以形成明确的专业分工。为解决这一问题，DeepSeekMoE 提出细粒度专家划分策略，**将原本较大的 FFN 专家拆分为多个更小的专家，并相应增加每个 Token 激活的专家数量。**

具体而言，假设传统 MoE 包含 16 个专家，每次激活 2 个。DeepSeekMoE 可以将每个专家拆分为 4 个小专家，使专家总数增加到 64 个，每次激活 8 个。每个小专家的 FFN 中间隐藏层维度缩小到原来的四分之一，因此专家总参数量与激活专家的计算量基本保持不变。

**这一设计的核心创新是，在不增加理论专家计算成本的前提下，显著提高专家组合的灵活性。** 例如，传统 Top-2 路由在 16 个专家中有 120 种组合，而从 64 个专家中选择 8 个，理论上存在约 44.26 亿种组合。这使模型能够更加灵活地组合不同专家，从而有利于不同知识被更精细地学习和利用。
## 2.2 共享专家隔离（Shared Expert Isolation）

传统 MoE 的所有专家通常都由路由器动态选择，不同专家可能重复学习语言基础知识等共通信息，造成参数冗余。为解决这一问题，DeepSeekMoE 提出共享专家隔离策略，**将部分专家设置为始终激活的共享专家，其余专家则继续通过路由器动态选择。**

共享专家负责学习不同输入共同需要的知识，路由专家则可以更加专注于特定知识。例如，在 64 个细粒度专家中，可以将 1 个设置为共享专家，剩余 63 个作为路由专家。每个 Token 固定激活共享专家，并由路由器另外选择 7 个专家，总激活数量仍为 8 个。

**这一设计的核心创新是将共通知识与专门知识分开学习，减少路由专家之间的知识冗余，从而提高专家专业化程度和参数利用效率。** 与细粒度专家划分相结合，DeepSeekMoE 同时改善了单个专家知识混杂和不同专家知识重复的问题。
## 2.3 完整架构与训练机制

DeepSeekMoE 将细粒度专家划分与共享专家隔离结合起来，形成由共享专家、路由专家和路由器组成的完整架构。对于每个 Token，共享专家始终参与计算，路由器则根据输入选择若干路由专家，各专家的输出最终进行加权求和。

此外，作者引入专家级负载均衡损失（Load Balance Loss），用于缓解路由坍缩问题，即大量 Token 集中分配给少数专家，导致其他专家得不到充分训练。该机制有助于维持专家的使用均衡，但并不是本文独有的主要创新。

**DeepSeekMoE 的主要架构贡献并非设计新的专家网络，而是重新组织 FFN 专家及其激活方式，使不同专家能够形成更加细致的知识分工。**
## 2.4 实验验证与模型扩展

作者首先构建了约 20 亿参数的 DeepSeekMoE 模型，通过与 GShard、Switch Transformer 等传统 MoE 架构比较，验证新架构的有效性。在相同总参数量与激活参数量下，DeepSeekMoE 的整体性能优于 GShard，并能够达到更大规模 GShard 模型的部分性能水平。

作者进一步通过消融实验和专家失活实验，分别验证细粒度专家划分与共享专家隔离的作用。实验发现，禁用高路由概率专家会导致 DeepSeekMoE 的性能明显下降，说明其专家具有更低的功能冗余；关闭共享专家后，其他路由专家也无法有效弥补其作用。

最后，作者将架构扩展至约 164 亿总参数的 DeepSeekMoE 16B，并使用 2 万亿 Token 进行预训练。**实验表明，DeepSeekMoE 16B 仅激活约 28 亿参数，在约 40% 的计算量下，取得了与 DeepSeek 7B 和 LLaMA2 7B 大体相当的性能。**

因此，本文不仅提出了改善专家专业化程度的架构设计，还通过不同规模的实验，验证了该方法在模型性能和计算效率方面的实际价值。
# 三、实验与结论
## 3.1 实验数据与设置

作者分别在 **20 亿参数（2B）和 164 亿参数（16B）** 两种规模下开展实验，以验证 DeepSeekMoE 的架构优势及其在更大规模模型上的有效性。

**第一组实验采用约 20 亿参数的模型，使用 1000 亿 Token 进行预训练。** 作者比较了 Dense、Hash Layer、Switch Transformer、GShard 和 DeepSeekMoE 五种架构。其中，DeepSeekMoE 与 GShard 均拥有约 20 亿总参数、3 亿激活参数，每处理 2048 个 Token 的计算量均为 4.3 万亿次浮点运算。

在相同计算成本下，两者的主要实验结果如下：

| 评测指标 | GShard | DeepSeekMoE |
| --- | --- | --- |
| Pile（损失，越低越好） | 1.867 | **1.808** |
| HellaSwag（准确率） | 50.5% | **54.8%** |
| PIQA（准确率） | 70.6% | **72.3%** |
| ARC-challenge（准确率） | 31.6% | **34.3%** |
| TriviaQA（精确匹配率） | 10.2% | **16.6%** |
| NaturalQuestions（精确匹配率） | 3.2% | **5.7%** |
作者还进行了两类消融实验，分别验证细粒度专家划分与共享专家隔离的作用。除此之外，论文通过禁用部分专家、调整激活专家数量等实验，进一步分析不同专家之间的知识冗余程度。

**第二组实验将 DeepSeekMoE 扩展至约 164 亿总参数，其中每次推理仅激活约 28 亿参数，并使用 2 万亿 Token 进行预训练。** 作者将其与 DeepSeek 7B 和 LLaMA2 7B 两种稠密模型进行比较，评估语言理解、数学推理、代码生成和知识问答等能力。

与 DeepSeek 7B 的主要对比结果如下：

| 评测指标 | DeepSeek 7B | DeepSeekMoE 16B |
| --- | --- | --- |
| 总参数量 | 69 亿 | 164 亿 |
| 激活参数量 | 69 亿 | 28 亿 |
| 每 4096 Token 计算量 | 183.5T | **74.4T** |
| Pile（BPB，越低越好） | 0.75 | **0.74** |
| HellaSwag | 75.4% | **77.1%** |
| GSM8K | 17.4% | **18.8%** |
| HumanEval | 26.2% | **26.8%** |
| MMLU | **48.2%** | 45.0% |
| C-Eval | **45.0%** | 40.6% |
## 3.2 实验数据说明了什么

**首先，DeepSeekMoE 在相同参数规模和计算成本下，整体性能优于传统 MoE 架构。** 在 2B 规模实验中，DeepSeekMoE 在全部列出的评测指标上均优于 GShard，尤其在 TriviaQA 和 NaturalQuestions 等知识问答任务上提升明显。这说明通过改善专家组织方式，可以更有效地利用已有的模型参数，而不必单纯依靠扩大模型规模。

其次，消融实验验证了两项核心设计的有效性。论文图 2 显示，在传统 GShard 基础上引入共享专家后，多数任务的性能得到改善；进一步增加专家划分粒度，模型性能又继续提升。**这表明细粒度专家划分和共享专家隔离均对模型性能有积极贡献，两者结合能够获得更好的效果。**

在专家专业化分析中，作者发现，禁用 DeepSeekMoE 中路由概率最高的专家，会导致模型性能比对照模型下降得更明显。同时，当共享专家被禁用、由额外路由专家替代时，Pile 损失从 1.808 上升至 2.414。**这些结果支持作者的判断：不同专家之间的功能冗余有所降低，共享专家也学习到了难以被路由专家直接替代的信息**。

最后，16B 规模实验表明，这种架构优势可以扩展至更大的模型。DeepSeekMoE 16B 的总参数量超过 DeepSeek 7B 两倍，但实际计算量仅约为后者的 40.5%，同时在语言建模、部分常识推理、数学和代码任务上取得相近或更好的结果。

**因此，本文最重要的实验结论是：改善专家专业化程度，可以在维持较低计算成本的同时，提高 MoE 模型的参数利用效率与整体性能。**
## 3.3 本论文的局限性

**第一，专家划分粒度受到实际计算效率的限制。** 尽管实验表明，将专家划分得更加细致通常能够改善模型性能，但过小的专家也会降低计算效率。因此，DeepSeekMoE 16B 仍采用适中的划分粒度。作者尚未确定不同模型规模下最优的专家数量与专家大小，也未建立相应的缩放规律。

**第二，更多专家参与计算可能增加设备之间的通信成本。** DeepSeekMoE 通过将大专家拆分为小专家，提高了每个 Token 激活的专家数量。当专家分布在不同 GPU 上时，更频繁的专家调用可能增加跨设备通信开销。因此，理论计算量的降低并不一定能完全转化为实际运行时间的降低，仍需改进并行计算与通信策略。

**第三，模型在部分任务上的表现仍然不足。** 虽然 DeepSeekMoE 16B 在整体性能和计算效率上取得了较好结果，但在 MMLU、C-Eval 和 CMMLU 等多项选择题评测中仍落后于 DeepSeek 7B。作者认为，这可能与模型中注意力模块的参数规模有限有关，说明增加专家参数并不能完全替代其他网络模块的能力。

此外，论文实验固定采用专家总参数量为标准 FFN 的 16 倍、激活专家参数量为标准 FFN 的 2 倍这一配置。**不同模型规模下，总专家参数量、激活专家数量与实际计算效率之间的最优关系，仍有待进一步研究。**
