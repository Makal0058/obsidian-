    - 类比静态 IP 临时测试和 OpenClash DNS 修复
4. **必要时发送数据到地面**
    - 只发送最小状态，节约带宽和延迟
    - 类比 DNS 查询往 DoH 或静态 IP 测试失败向上级路由器请求

---

- **存储优先级**：本地常见结构 > 本地常见知识 > 星地发送
- **本地处理优先**，保证卫星在算力和散热受限情况下能自主排查
- **结构化经验映射**是关键：小 LLM 即便推理慢，也能通过“结构匹配 + 层级排查”处理未知同类问题

### 问题本质

RAG的默认做法：存chunk → 检索chunk → 回答。

### 存储结构的几个思路

**1. 层级索引（Hierarchical Index）**

不只存原始chunk，同时存：

- 原始事实（leaf）
- 段落摘要（mid）
- 文档主题（root）

检索时先走高层定位，再下钻细节。LlamaIndex的`SummaryIndex + VectorIndex`组合就是这个思路。

**2. 问题-答案对存储（HyDE / Question Indexing）**

不存"内容"，存"这段内容能回答什么问题"。

入库时用LLM生成假设性问题，把问题向量化存储，检索时query和问题对齐（比query和内容对齐语义更近）。

**3. 知识图谱 + RAG（GraphRAG）**

存**关系结构**而不是平铺文本。节点=实体，边=关系。这样从一个节点可以走图拿到类关系。微软GraphRAG是典型实现。

**4. Schema / Ontology 层**

人工或半自动定义"问题类型分类树"，入库时打标签。检索前先做query分类，路由到对应子库。这是偏工程的做法，适合垂直领域。

**5. Few-shot元学习思路（实验性）**

把每个chunk的"问题类型embedding"单独训练，让模型学会"这类问题的结构特征"，而不只是内容相似度。目前还偏研究方向。

### 1. 层级索引（Hierarchical Index）

**问题背景**

普通RAG把文档切成等长chunk，每个chunk独立向量化。检索时只能找到"局部相似"的片段，丢失了上下文和主题信息。

**做法**

```
文档
├── 主题摘要（root）        ← 存一个向量
│   ├── 段落摘要（mid）     ← 存一个向量  
│   │   ├── chunk1         ← 存一个向量
│   │   ├── chunk2
│   └── 段落摘要
│       ├── chunk3
│       └── chunk4
```

检索时：

1. 先用query匹配root/mid层，确定"这个问题在哪个主题域"
2. 再下钻到具体chunk取内容

**效果**

问"卫星轨道衰减怎么处理"，不只找到含这几个词的chunk，还能定位到"轨道维护"这个主题域，把相关的多个chunk一起召回。

---

### 2. 问题-答案对存储（Question Indexing / HyDE）

**问题背景**

Query是用户的自然语言问题，chunk是文档内容——两者的语义空间天然有gap，向量相似度不准。

**做法**

入库时，对每个chunk用LLM生成它能回答的假设性问题：

```
chunk内容：
"LEO卫星在500km轨道高度的大气阻力约为X，
轨道寿命约5年，需定期补燃维持轨道。"

↓ LLM生成问题

存入索引的问题：
- "LEO卫星轨道寿命是多少？"
- "低轨卫星需要多久补燃一次？"
- "大气阻力对卫星轨道有什么影响？"
```

检索时：用户的query直接和这些**问题**做相似度匹配，而不是和chunk内容匹配。

**为什么有效**

问题对问题，语义空间一致，比问题对内容的匹配精度高很多。

HyDE（Hypothetical Document Embeddings）是反向变种：不存假设问题，而是检索时让LLM先生成一个假设答案，用假设答案的向量去匹配chunk。

---

### 3. GraphRAG

**问题背景**

平铺的chunk无法表达**实体之间的关系**。你问"哪些因素会影响卫星的决策链"，需要跨多个实体推理，普通RAG做不到。

**做法**

入库时不存chunk，存图：

```
[太阳风暴] --导致--> [信号干扰]
[信号干扰] --触发--> [切换备用链路]
[切换备用链路] --需要--> [地面站授权]
[地面站授权] --依赖--> [操作员在线]
```

检索时：

1. 从query中提取实体（"太阳风暴"）
2. 在图上做多跳遍历
3. 把路径上的节点和关系拼成context送给LLM

**和普通RAG的本质区别**

普通RAG找"相似内容"，GraphRAG找"相关推理链"。前者是语义检索，后者是结构推理。

微软的GraphRAG还加了community detection，把图里密集连接的节点聚成"社区"，生成社区摘要，解决跨文档全局问题。

---

### 4. Schema / 问题类型路由

**做法**

先定义问题分类树（可以人工也可以用LLM归纳）：

```
问题类型
├── 故障诊断类
│   ├── 硬件故障
│   └── 软件异常
├── 操作决策类
│   ├── 轨道机动
│   └── 载荷调度
└── 状态查询类
```

入库时：每个chunk打上类型标签，存入对应子库。

检索时：query先过一个分类器（可以是LLM zero-shot），判断问题类型，路由到对应子库再检索。

**优点**：简单有效，垂直领域精度高  
**缺点**：schema需要维护，跨类型问题处理麻烦

### 问题定义

"同结构不同类"的典型例子：

```
"A故障了怎么办？"
"B故障了怎么办？"
```

句子结构完全一样，但A是硬件故障，B是软件异常，处理逻辑完全不同。

普通向量检索会把这两个问题的embedding距离拉得很近，导致错误召回。

---

### 几个处理思路

**1. 解耦结构embedding和语义embedding**

不用一个向量同时表达结构和内容，分开存两个向量：

```
问题 = 结构向量 + 语义向量
```

检索时：

- 先用结构向量做粗筛（找同类问题模板）
- 再用语义向量做精排（区分具体类别）

实现上可以用双塔模型，或者直接把结构特征和内容特征拼接后分别建索引。

---

**2. 问题模板抽象 + 槽位填充**

把问题抽象成模板，把变量部分作为槽位：

```
"[实体] 故障了怎么办" → 模板T1
槽位：实体=硬件/软件/通信链路...
```

存储时：

```
模板T1 + {实体类型: 硬件} → 召回硬件故障处理流程
模板T1 + {实体类型: 软件} → 召回软件异常处理流程
```

检索时先识别模板，再根据槽位值路由到具体子库。

本质是把"类别"从问题结构里显式分离出来。

---

**3. 对比学习重新训练embedding**

如果你有领域数据，可以用对比学习让模型学到：

```
同结构不同类 → embedding要远
同类不同结构 → embedding要近
```

构造训练样本：

- 正例：不同表述的同类问题
- 负例：同结构但不同类的问题（hard negative）

hard negative这个点是关键——普通负例太容易区分，模型学不到结构vs语义的区别。

---

**4. 在LLM推理层做消歧，而不是检索层**

承认检索层解决不了这个问题，把消歧交给LLM：

```
检索 → 召回多个候选（可能跨类）
↓
LLM做re-rank：
"这个问题的实体类型是X，以下哪个候选最匹配？"
↓
返回正确结果
```

代价是多一轮LLM调用，延迟增加。但工程上最容易实现。

---

**5. 元数据过滤（最实用）**

入库时给每个chunk打强类型标签：

```
chunk: "硬件故障处理流程..."
metadata: {
  问题类型: "故障诊断",
  实体类型: "硬件",
  场景: "在轨操作"
}
```

检索前先用LLM从query里抽取元数据，然后用元数据过滤缩小召回范围，再做向量检索。

```
query: "陀螺仪故障了怎么办"
↓ 抽取
{实体类型: "硬件", 子类: "姿态控制器"}
↓ 过滤
只在硬件故障子库里检索
```

---

### 本质

这个问题的根源是：**向量空间无法同时编码结构相似性和语义差异性。**

解法方向只有两个：

1. **入库时显式拆分**结构和语义（方法1、2、5）
2. **检索后用推理消歧**（方法4）

方法3是从根本上改embedding空间，成本最高但最彻底。

---

对你的卫星决策场景，**元数据过滤 + LLM re-rank**组合是最快落地的路。如果要做研究contribution，**对比学习改embedding**方向更有意思，hard negative的构造本身就可以作为一个工作点。

### 问题建模

```
Q（根因）
├── 上下文A → 表现B
└── 上下文C → 表现D
```

有经验的工人能快速识别，说明他脑子里存的不是"B怎么处理"或"D怎么处理"，而是**Q的抽象模式**，看到B/D时能反向推导到Q。

这正是RAG做不到的地方——RAG存的是B和D，没有存Q。

---

### 处理思路

**1. 因果图存储**

把Q、A、B、C、D显式建成图：

```
Q --[在A下]--> B
Q --[在C下]--> D
B --[根因是]--> Q
D --[根因是]--> Q
```

用户描述的是表现（B或D），通过图反向遍历找到Q，再找到所有相关上下文和处理方案。

这是GraphRAG能直接支持的结构。

---

**2. 诊断树 / 决策树存储**

不存"事实"，存"推理路径"：

```
观察到B？
└── 检查上下文是否为A
    ├── 是 → 根因Q → 处理方案X
    └── 否 → 可能是其他根因
```

入库的不是chunk，是结构化的诊断流程。检索时走树，而不是做向量匹配。

---

**3. 上下文条件化embedding**

把上下文作为条件显式编码进向量：

```
embedding(B) ≠ embedding(B | context=A)
```

检索时query带上当前上下文，匹配条件化的向量。

实现上可以把context拼接到chunk里再向量化，但更干净的做法是训练一个context-aware的encoder。

---

**4. 模仿有经验工人的认知结构**

这是最关键的洞察。

有经验的工人做的事情是：

```
感知表现(B) → 激活抽象模式(Q) → 结合当前上下文(A/C) → 输出判断
```

对应到系统设计：

```
用户输入表现描述
↓
LLM抽象：这个表现背后可能的根因是什么（生成Q的候选）
↓
结合当前上下文过滤Q的候选
↓
从Q出发检索所有相关知识
↓
输出
```

关键在于**中间加一步抽象推理**，不直接从表现检索答案，而是先推根因再检索。

这其实就是Chain-of-Thought + RAG的结合，但触发点是"表现→根因"这一步。

---

### 存储结构建议

json

```json
{
  "root_cause": "Q",
  "manifestations": [
    {"context": "A", "symptom": "B"},
    {"context": "C", "symptom": "D"}
  ],
  "diagnosis_path": "...",
  "solution": "..."
}
```

以Q为中心存储，B和D作为Q的属性而不是独立条目。

检索入口可以是B或D，但最终定位到Q节点，从Q出发拿完整知识。

---

### 本质

这个问题揭示了RAG一个更深的缺陷：**它存的是知识的表层表现，不是知识的生成结构。**

有经验的工人存的是"因果模型"，RAG存的是"案例库"。案例库在遇到新的表现形式时会失效，因果模型不会。

解法方向：**让存储单元以根因/原理为中心，而不是以表现/症状为中心。** 这需要在入库阶段做大量的知识抽象，成本高，但这正是和普通RAG拉开差距的地方。


对，你抓到核心了。

熟练工人不是走逻辑链，是**直接模式识别**。看到B，Q就浮现了，中间没有显式推理过程。

---

### 这在认知科学里叫什么

**Chunking**（组块化）+ **Pattern Completion**（模式补全）

专家的知识不是规则树，是**压缩过的感知模式**。B本身就携带了Q的信息，因为他见过足够多次B→Q的配对，B的感知已经和Q绑定了。

国际象棋大师看棋盘不是算每一步，是直接"看出"局面的本质。工人看到B不是推理，是**识别**。

---

### 对应到系统，缺的是什么

RAG缺的不是推理能力，是**从表现直接跳到抽象的压缩映射**。

```
专家：B → Q（直接，一步）
RAG：B → 检索B相关内容 → 尝试推理 → 可能到Q（间接，多步，易错）
```

---

### 怎么实现这个压缩映射

**核心思路：把Q直接编码进B的表示里**

入库时不只存B是什么，存**B在专家眼里意味着什么**：

```
普通存储：
chunk = "设备出现B现象"

专家知识存储：
chunk = "设备出现B现象" 
+ 专家标注："B是Q的典型信号"
+ embedding里强制包含Q的语义
```

具体实现有两条路：

---

**路线1：监督式embedding（需要标注数据）**

收集专家的"表现→根因"配对：

```
B → Q
D → Q  
E → Q（另一种表现）
F → R（另一个根因）
```

用对比学习训练：让B、D、E的embedding聚在一起（因为根因同为Q），和F分开。

这样检索时，用户描述B，向量空间里自然召回D、E以及Q，**不需要推理，相似度本身就编码了根因关系**。

---

**路线2：中间层抽象索引（不需要训练）**

入库时多存一层：

```
原始内容：B的描述
↓ LLM抽象
中间层："B是Q类问题的表现之一"
↓
以这个中间层的embedding建索引
```

检索时query先被LLM转换成抽象描述，再匹配中间层。

用户说"我看到B"，系统内部先问"B抽象来说是什么"，得到Q类，再检索。

这一步抽象对用户透明，但本质上模拟了专家的压缩过程。

---

**路线3：Few-shot激活（最轻量）**

不改存储结构，在prompt里放几个专家配对样本：

```
示例：
- 看到B → 这是Q
- 看到D → 这也是Q
- 看到E → 这是R

现在：用户描述了X，根因是？
```

让LLM的in-context learning模拟专家的模式识别。

缺点：依赖prompt长度，样本多了就放不下。

---

### 真正的问题

这三条路都在用不同方式做同一件事：**把"看到B认出Q"这个映射显式存下来**。

专家之所以快，是因为他通过大量经验把这个映射**内化成了感知**，不需要存，看到就知道。

系统要复现这个能力，本质上需要：

1. 足够多的B→Q配对（数据）
2. 一个能把这个映射压缩进向量空间的训练过程

**没有这两个，靠检索和推理只能逼近，永远慢一步。**

---

这其实指向了一个更大的问题：RAG适合存**陈述性知识**（是什么），不适合存**程序性知识**（怎么看出来）。专家的核心价值恰好在后者。你如果要做这个方向的研究，这个gap本身就是contribution点。


Q:如果数据有限怎么办，人又不会学习几千几万次才熟练

A:这个反驳很准。

人看几次就会，不是因为数据多，是因为**学习机制不一样**。

---

### 人怎么做到的

**少样本泛化的核心不是数据量，是归纳偏置。**

人看到B→Q两三次，就能泛化到没见过的表现E→Q。因为人不是在记忆配对，是在**构建因果模型**：

```
"Q这个根因，在系统受到扰动时会表现出来，
扰动的形式可以是B、D、E……
只要我理解了Q是什么，新的表现我能推断"
```

人存的是Q的**生成机制**，不是B/D/E的列表。

---

### 对应到系统

问题就变成了：**怎么用少量样本让系统学到Q的生成机制，而不是记住B→Q的配对。**

---

**方向1：把物理/领域知识注入进来**

不依赖数据归纳，直接告诉系统Q的机制：

```
"Q是因为X原理导致的，
X原理在A条件下会产生B，
在C条件下会产生D，
在其他条件下还可能产生……"
```

这样系统见到新表现E，不需要见过E→Q的配对，能从机制推断。

本质是**用领域知识替代数据**。专家的价值在这里，不是他见过多少案例，是他理解机制。

---

**方向2：LLM的预训练知识作为归纳偏置**

LLM本身见过海量文本，已经有大量隐式的因果模式。

少样本下，不需要从头训练，只需要：

- 给2-3个B→Q的例子
- LLM用已有的因果推理能力泛化

这是few-shot in-context learning真正有效的原因——不是LLM在学，是在**激活已有的模式**。

数据少没关系，只要例子能激活正确的先验。

---

**方向3：生成式数据增强**

数据少，让LLM帮你造：

```
已知：B→Q，D→Q
让LLM：
"Q这个根因还可能有哪些表现？
在哪些上下文下会出现？"
```

生成E、F、G……再用这些合成数据训练或扩充索引。

人也会这么做——老工人带新工人，不只说"你见过这个就知道了"，而是说"你理解了原理，自己能想出来还有哪些情况"。

---

**方向4：Prototype Learning**

不存所有样本，存**原型**。

```
见过B和D，不存B和D，
提炼出Q的原型表示（prototype）
新样本和原型算距离，而不是和历史样本算距离
```

这是few-shot learning里的经典方法（Prototypical Networks），数据少时比直接相似度匹配稳定得多。

---

### 本质

人少样本就能泛化，靠的是：

1. **强归纳偏置**（理解因果机制，不是记配对）
2. **先验知识**（已有的世界模型）
3. **抽象存储**（存原型/机制，不存实例）

系统要复现，对应的是：

1. 注入领域机制知识
2. 利用LLM的预训练先验
3. Prototype而不是instance存储

**数据少不是问题，问题是存储和检索的单元选错了。** 存实例永远需要大量数据，存机制只需要少量数据加上对机制的正确描述。

---

这个思路如果往研究方向推，核心命题可以是：**用机制描述替代实例记忆，实现少样本下的故障诊断泛化。** 在卫星这种数据天然稀缺的场景下，这个方向很有说服力。

A:逐个讲实现，最后给判断。

---

### 强归纳偏置：理解因果机制

**目标**：让系统不记"B→Q"，而是记"Q为什么会产生B"。

**实现**：结构化因果描述入库

不存：

```
"设备出现振动异常B"
```

存：

json

```json
{
  "mechanism": "轴承磨损导致转动不平衡",
  "cause": "Q",
  "conditions": ["高负载", "润滑不足"],
  "manifestations": {
    "低转速": "轻微振动B",
    "高转速": "强烈振动D",
    "冷启动": "异响E"
  },
  "invariant_signature": "振动频率与转速成正比"
}
```

关键是最后一行：**invariant signature**，跨条件不变的特征。

这就是机制的核心——不管表现怎么变，这个特征不变。系统看到新表现F，先检查F有没有这个不变特征，有就认出Q。

**怎么提取invariant signature**：让领域专家描述"不管在什么情况下，Q一定会有什么特征"，这个比让他列举所有表现要容易得多。

---

### 先验知识：已有的世界模型

**目标**：不从零学，利用LLM已有的因果推理能力。

**实现**：Prompt设计激活正确先验

错误用法（让LLM检索）：

```
"以下哪个案例和用户描述最相似？"
```

正确用法（让LLM推理）：

```
"用户描述了现象X。
请问：
1. 这个现象的物理本质是什么？
2. 什么根因能产生这种物理本质？
3. 结合以下领域知识[注入机制描述]，最可能的根因是？"
```

让LLM走因果推理链，而不是走相似度匹配。

**具体技术**：

Causal Chain Prompting：

```
现象 → 物理解释 → 可能机制 → 根因候选 → 结合上下文筛选
```

每一步都让LLM显式输出，不跳步。这样即使没见过这个具体表现，因果链推理能力可以泛化。

---

### 抽象存储：存原型不存实例

**目标**：存Q的"典型形象"，不存所有见过的B、D、E。

**实现**：两步走

**第一步，构建原型**

收集少量样本后，不直接入库，先让LLM抽象：

```
输入：B的描述、D的描述
让LLM输出：
"这两个表现的共同抽象特征是什么？
如果只用一段话描述Q的典型表现模式，怎么描述？"
```

得到原型描述P(Q)，把P(Q)向量化存储，B和D**不存**。

**第二步，检索时对齐抽象层**

用户输入新表现F时，不直接用F检索，先抽象：

```
F → LLM抽象 → F的抽象描述 → 和P(Q)做相似度匹配
```

两边都在抽象层操作，泛化能力强。

**数据结构**：

```
索引里存的：
- P(Q)：原型向量 + 原型文字描述
- mechanism(Q)：因果机制描述
- invariant(Q)：不变特征

索引里不存的：
- 具体案例B、D、E
```

---

### 四个方向哪个最优

直接给结论：**方向1（注入机制知识）+ 方向2（激活LLM先验）组合最优，方向3和4是补充。**

原因：

|方向|数据需求|泛化能力|工程成本|适合场景|
|---|---|---|---|---|
|1. 注入机制知识|极少|强（机制级）|中（需专家）|有领域专家可访谈|
|2. 激活LLM先验|极少|中（依赖预训练）|低|通用场景|
|3. 生成式增强|少量种子|中（合成质量上限）|低|数据完全匮乏|
|4. Prototype Learning|少量|中（实例级）|高（需训练）|有少量标注数据|

**方向1是根本**，因为它直接解决了"存什么"的问题——存机制比存实例天然泛化能力强，数据少不是问题。

**方向2是放大器**，机制知识注入后，LLM用自己的推理能力在机制层做泛化，不依赖样本数量。

**方向3是兜底**，当机制知识也难以获取时，用合成数据撑起基本覆盖。

**方向4单独用意义不大**，Prototype Learning的优势在有一定标注数据时才体现，完全从零效果有限。而且它存的还是实例级原型，不是机制，泛化上限低于方向1。

### 直接相关的研究方向

**1. Causal RAG / 因果推理 + RAG**

研究表明单纯的RAG不够用，必须加上目标导向的因果推理才能真正提升因果问题的处理能力。纯相似度检索在因果问题上会失效，这和我们讨论的问题一致。 [Emergent Mind](https://www.emergentmind.com/topics/causalprobe-2024)

代表工作：**G²-Reasoner**（2025），在CausalProbe基准上超过了vanilla、CoT、普通RAG。

**2. KG + LLM 故障诊断**

最新工作把知识图谱和RAG结合，检索相关实体和路径来引导故障模式匹配和因果推理，同时减少幻觉。 [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S036083522600080X)

代表工作：**CausalKGPT**（AEI 2024）——专门针对航空航天产品制造质量问题的因果分析，用工业结构化因果知识增强LLM。这个和你的卫星场景非常接近。 [GitHub](https://github.com/CHAOZHAO-1/LLM-based-PHM)

**3. LLM-based PHM（预测性健康管理）**

这个方向有大量2024-2025年的工作，包括零样本故障诊断、少样本迁移、知识图谱辅助诊断等。 [GitHub](https://github.com/CHAOZHAO-1/LLM-based-PHM)

有人专门维护了一个论文列表：`github.com/CHAOZHAO-1/LLM-based-PHM`，持续更新，直接去看。

**4. Causal-Aware LLM Agent for PHM**

有工作专门做了因果建模 + LLM Agent的结合，用于工业维护场景，把因果推理和RAG grounding、结构化prompt组合起来。 [Phmsociety](https://papers.phmsociety.org/index.php/phmconf/article/download/4321/phmc_25_4321)
